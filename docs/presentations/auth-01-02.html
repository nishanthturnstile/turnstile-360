02 / ACCOUNT & SESSION LIFECYCLE

A real account can sign in,
persist and recover.

This lifecycle works at the DMS authority and has been exercised with fixture users. Select a step to explore.

Private operator provisioning

An operator creates the account through a local command with JSON on stdin. Public signup is closed. New addresses remain unverified; no bootstrap password is printed or passed in command arguments.

PASSWORD RESET · ONE DATABASE TRANSACTION
Consume reset token→Revoke sessions→Write password

All succeed together. An injected database failure proved all three changes roll back. A retry succeeds once; replay is rejected.

Safe public responses

Sign-in/session JSON excludes raw session tokens and internal credentials. HttpOnly cookies carry authority sessions.

Controlled recovery

Verification and reset links expire in 30 minutes. SMTP failures return a controlled unavailable response.

Native handler also preserves redirects and multiple cookies, accepts JSON/form bodies and denies raw account/client administration routes. Product login UI is pending.

02 / PERSISTENCE & SECURITY BOUNDARIES

Each data owner
has a narrow set of keys.

Three ownership boundaries, each with a separate runtime role, migrator role and migration history.

OwnerRuntime accessTenant protection
auth13 generated tablesCRUD on owned auth tablesSessions, keys, accounts, protocol stateBetter Auth global semanticsSeparate from DMS tenant RLS
dmsInstallation + registrationsRegistration CRUDInstallation identity is read-onlyForced RLS on registrationsExplicit transaction-local tenant
turnstileIdentity, access + sessionsSession CRUDIdentity and user access are read-onlyForced RLS on access/sessionsExplicit transaction-local tenant

Runtime cannot change the schema

No DDL, temporary tables, truncation, migrator membership or access to another owner’s schema. Migrations run explicitly through private operator commands.

Product sessions are encrypted

SHA-256 session identifiers and AES-256-GCM payloads. Tenant/ID-bound integrity checks and atomic updates prevent stale saves from undoing logout.

Installation identity is fixed. Matching bootstrap can be repeated safely. A different tenant or customer is rejected. Product access defaults to disabled.

Role capabilities and schema isolation were checked against real PostgreSQL. Authority and product pools are separately owned; application startup does not migrate or provision accounts/clients.
